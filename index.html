Fork notes for the Wikijump maintainer

Snapshot of the Rokurolize forks of Wikijump and ftml from 2026-11-25.

Specimen pull requests Capability comparison Roadmap alignment Extraction method

On 2026-11-25, the Rokurolize forks of Wikijump and ftml held 47 small demonstration pull requests open on the forks (none submitted upstream). Below are the index of those pull requests, a capability comparison between upstream and the fork, a mapping of unfinished items on upstream's Project Foundation roadmap against what the fork can demonstrate, and the extraction method behind the pull requests.

Specimen pull requests

A live check on 2026-11-25 found 47 open pull requests across the two forks: 33 in Rokurolize/wikijump and 14 in Rokurolize/ftml. Each summary comes from the pull request's own title and body and notes both the defect and its user-visible effect.

ftml, original-wiki and Wikidot-layout behavior

Measured against live Wikidot or the original wiki; two were explicitly reproduced in the Wikidot layout.

  • ftml#1424, ftml: Spaces inside raw spans render as literal spaces in the Wikidot layout instead of Wikidot's &#32;. Authors and readers comparing the two renderings see a byte-level difference.
  • ftml#1530, ftml: Multi-word element ids get prefixed on every word instead of once as a whole, breaking anchors, links, and scripts that target the live Wikidot id.
  • ftml#1534, ftml: A local page whose name looks like a URL scheme, such as data:example, renders as #invalid-url instead of a local page link, leaving the page unreachable through ordinary links.
  • ftml#1565, ftml: Uppercase and lowercase spellings of the same hex color serialize differently instead of sharing Wikidot's lowercase form. Equivalent author input produces different markup.

ftml, parser and renderer correctness

  • ftml#1427, ftml: A triple-bracket link with an empty label and a direct target panics the renderer. One author mistake can make an entire page unavailable.
  • ftml#1510, ftml: A block name with two trailing underscores, such as [[div__]], crashes the parser instead of producing a parse error, leaving readers with an error page instead of the article.
  • ftml#1511, ftml: Overlapping [[include]] directives can clobber replacement ranges or panic the renderer, leaving readers with broken content or no page.
  • ftml#1517, ftml: An include whose page reference is only a separator is accepted with an empty page name instead of rejected. That causes an unintended fetch or a misleading missing-page result.
  • ftml#1536, ftml: A bibliography citation whose label is only whitespace produces a broken reference without a parse error. Authors get no warning, and readers hit a citation that leads nowhere.
  • ftml#1537, ftml: A whitespace-only category condition silently renders its body instead of returning a parse error, so content that should have been filtered can appear.
  • ftml#1538, ftml: A list whose only item line is whitespace renders empty list tags with no parse error; the intended list disappears without warning.
  • ftml#1539, ftml: A ruby annotation with an empty base or reading renders a half-empty pronunciation guide without a parse error, leaving visibly broken markup.
  • ftml#1564, ftml: Leading document whitespace can prevent a quote or list marker on the first non-empty line from parsing as structure. Saved pages render the marker as plain text.
  • ftml#1566, ftml: The null includer reports an internal invalid-return error instead of removing include blocks, so tests and tooling that render without fetching includes get no page at all.

Wikijump, browser-visible page and file workflows

  • wikijump#3908, wikijump: Saving site settings fails on an imported site whose site-user relation still uses the legacy user spelling, rejecting an administrator's ordinary settings edit.
  • wikijump#3911, wikijump: A delayed initial file-list response can overwrite the deleted-file list after Restore is opened, wiping out the deleted rows and Restore controls a moderator was using.
  • wikijump#3912, wikijump: Racing revision requests can let an older answer overwrite a newer one. A reader comparing revisions ends up seeing a revision they did not select last.
  • wikijump#3913, wikijump: A late file-history response is not bound to the requesting file, letting one attachment display another attachment's revisions and Revert controls.
  • wikijump#3918, wikijump: The Files pane's Revert control requests an action that is implemented but never registered. Clicking it gives the editor a 404 instead of a rollback.
  • wikijump#3919, wikijump: Saving a file edit omits the client address required by the backend audit call; every save from the Files pane fails with a parameter error.
  • wikijump#3927, wikijump: An anonymous Restore form submission fails for missing user_id instead of returning a clean permission error, showing the visitor a raw server error.
  • wikijump#3936, wikijump: Tags submitted through the create form or page_create API are silently discarded. Newly created pages end up with no tags even though later edits save them normally.
  • wikijump#3986, wikijump: The fileList action ignores its page and perPage arguments and returns every file on every call, making large attachment lists unnecessarily expensive for clients.
  • wikijump#3990, wikijump: The deleted-page Restore form always submits page id 0 regardless of the selected radio button. The restore fails and the page stays deleted.

Wikijump, sessions, routing, and request-boundary validation

  • wikijump#3881, wikijump: A NUL byte in a page name or RPC string parameter turns ordinary lookups into internal errors; an unauthenticated crafted URL can trigger a site-wide 500 response.
  • wikijump#3915, wikijump: A stale or invalid session cookie causes every page to return HTTP 500 until the visitor clears cookies manually, while the same pages work without the cookie.
  • wikijump#3934, wikijump: A slug containing a character above U+00FF cannot be carried in the internal page header. Japanese and other non-Latin-1 page URLs return 500 and cannot be created through the form.

Wikijump, authentication, authorization, and permission boundaries

  • wikijump#3882, wikijump: A soft-deleted user can still log in and receive a fresh session; administrative deletion does not lock the account out.
  • wikijump#3943, wikijump: A user without delete permission can delete and restore another user's page, with both state changes attributed to the unauthorized account.
  • wikijump#3947, wikijump: A user denied edit access can still roll a page back, silently altering revision state visible to anonymous readers.
  • wikijump#3952, wikijump: A non-member can change another page's layout, rename it, and set its parent because none of those mutations checks edit permission first.
  • wikijump#3953, wikijump: A non-member without lock permission can create and remove page locks, changing whether editors can use the page.
  • wikijump#3954, wikijump: An authenticated user can create a page in a foreign site by supplying that site's id, placing a page where the user has no create permission.
  • wikijump#3957, wikijump: A logged-in outsider can read another site's wikitext, revision history, and file list through page read actions that omit the view-permission check.
  • wikijump#3958, wikijump: File revision history ignores the requested site and page, allowing an outsider to read another site's file revisions by supplying identifiers.
  • wikijump#3959, wikijump: A user with no site role can delete, restore, move, and upload files on another page or site because those file mutations omit the page-edit-permission check.
  • wikijump#3960, wikijump: A user with no site role can overwrite another site's settings, including its tagline, by supplying that site's numeric id.

Wikijump, votes and deleted-page state

  • wikijump#3955, wikijump: The vote API still accepts vote changes, disabling, and removal on deleted or missing pages, letting ratings keep moving on content that no longer exists.
  • wikijump#3956, wikijump: The vote API accepts any 16-bit value instead of limiting votes to -1 and 1, letting undefined vote values distort computed scores.

Wikijump, file serving, error pages, and information exposure

  • wikijump#3879, wikijump: Direct requests to the files service without its internal routing headers panic the handler and drop the connection instead of returning an HTTP error response.
  • wikijump#3880, wikijump: A crafted files-origin error URL interpolates request text into HTML without escaping, executing script for a victim who follows the link.
  • wikijump#3909, wikijump: Uploaded files are stored and served with a byte-sniffed content type instead of the browser-declared one, so visitors get a different Content-Type than the upload declared.
  • wikijump#3935, wikijump: A well-formed but missing text-block index panics the handler and produces an empty 502 instead of a clean error response.
  • wikijump#3961, wikijump: A file URL containing a NUL byte returns a 500 error page reflecting the NUL instead of a normal 404.
  • wikijump#3962, wikijump: An avatar URL with a non-numeric id returns an empty 500 response instead of the normal templated 404.
  • wikijump#3987, wikijump: Named-action failures can expose Rust source paths, line numbers, or raw PostgreSQL driver text in client-visible error traces, leaking implementation detail to ordinary callers.

Wikijump, dependency security

Dependency update with no local behavioral reproduction.

  • wikijump#3883, wikijump: Vite 7.3.7 is affected by a critical dev-server remote-code-execution advisory when the server is exposed to the network. This moves the dependency to the patched 7.3.8 release.

Decision points disclosed in the pull requests

Two pull requests ask the maintainer for a judgment call: wikijump#3883 rests on the published Vite security advisory and a resolved-version assertion with no local behavioral test, and wikijump#3954 lays out guard-shape choices for the maintainer to judge. A missing category returns a hard error instead of falling back to an invented category 0, the internal system actor stays exempt so seeding and migrations keep working, and the pull request flags an untested bypass risk from a caller-supplied system id.

Stage 1 (Foundations), epic WJ-1256, live status Backlog

1. "All UI available so far is properly localized (i.e. no UNTRANSLATED)"

  • Jira status: WJ-1262, "Ensure all UI is properly localized", Backlog.
  • Upstream today: partial. A scan of the upstream base found UNTRANSLATED in 16 files under framerail/src, deepwell/src, or locales/fluent; upstream /about itself displays UNTRANSLATED: Info page and UT: labels.
  • Fork today: the same scan found no UNTRANSLATED marker in the inspected fork trees. The fork has 53 Fluent files, and the running fork-backed local mirror rendered /-/about in localized English or Japanese depending on the site.
  • Extraction prospect: demonstration. This is broad cumulative UI work. The fork can show localized pages and translation keys, while upstream would still need its own review of coverage and missing languages.

2. "All infrastructure is available through IPv6"

  • Jira status: WJ-1261, "Ensure Wikijump is fully IPv6-capable", Backlog.
  • Upstream today: unproven. The upstream tree includes local IPv6 bind examples such as [::1]:2747 and PostgreSQL ::1/128 rules, with no evidence of end-to-end public IPv6 deployment.
  • Fork today: no meaningful advantage. The fork carries the same local examples and no additional proof of full IPv6 infrastructure.
  • Extraction prospect: not applicable. The work is primarily deployment and network validation, leaving no portable code to extract.

3. "Page theme exposure"

  • Jira status: no directly corresponding issue was found in the stage epic; WJ-113 "Base theme support" is Backlog outside the stage epic.
  • Upstream today: partial. Upstream exposes page and site layout selection (Layout::Wikidot or Layout::Wikijump) in LayoutPane.svelte and the admin screen, and framerail/src/routes/+layout.svelte hardcodes a Sigma-style Wikidot base-theme import, with no theme-management or per-category selection surface found.
  • Fork today: ThemeSettings.svelte exposes theme type, built-in theme, external URL, and custom CSS fields by category; the fork also has theme evidence and replay tooling in install/local/theme-lab/ and docs/agents/theme-lab.md.
  • Extraction prospect: demonstration. The fork demonstrates a working theme model and imported theme evidence, but the implementation depends on the fork's larger Wikidot shell and category model and cannot be lifted as a small patch.

4. "Temporary support for passcode to limit user creation" (unchecked child of the completed user-creation UI item)

  • Jira status: no exact issue found. Related WJ-1153, "Add platform setting to deny new user creation", is Backlog.
  • Upstream today: no passcode flow found. Upstream has an authorization-token type whose comment says it can authorize user creation when registrations are disabled, which does not provide passcode-based self-service registration.
  • Fork today: no passcode flow found. The fork has an allow_registration configuration switch and registration rate limiting in deepwell/src/endpoints/user.rs, neither of which implements the roadmap's temporary passcode mechanism.
  • Extraction prospect: not applicable. This is a small upstream product decision and implementation; the fork has no working passcode flow to demonstrate.

5. "Basic platform settings UI" and "Able to set free creation or requiring a passcode"

  • Jira status: related WJ-1153 is Backlog; no direct settings-UI issue was found.
  • Upstream today: no platform settings UI found. The upstream admin route manages individual sites, with no platform-wide registration policy controls.
  • Fork today: partial backend evidence only. deepwell/src/config/file.rs supports allow_registration, and deepwell/src/endpoints/info.rs exposes registration_open, but no browser platform-settings panel or passcode setting was found.
  • Extraction prospect: not applicable. The fork shows a registration switch is feasible, without demonstrating the requested settings UI or passcode mode.

6. "Basic user settings UI" and "Able to modify a user's email and password"

Extraction method

The extraction produced small, reviewable defect demonstrations from the long-lived Rokurolize/wikijump and Rokurolize/ftml forks.

Starting point

Fork implementations were treated as evidence for finding defects, without attempting to upstream fork code wholesale. Each portable pull request proves one behavior against unmodified upstream (a failing input, request, browser workflow, API call, or externally published advisory) and pairs it with a small native correction.

Upstream base commits were fixed before extraction. Wikijump pull requests were cut from upstream commit 324cbef61145aadcf016ff6e8e4a8c83cdae48f0; later ftml pull requests were cut from 3ea7d6d00995ee6c0b7fc32fa50f38a5eb2446dc, with the two earliest ftml entries originally cut from the immediately preceding mirror base 81552b44d3da5a1daea1bf43f4d5fa9b5c1a5cbe. Before running behavioral reproductions, a local unmodified-upstream test stack was rebuilt and reseeded at the wikijump base.

How prospective defects were found

Potential defects came from several independent sources, including earlier records, issue trackers, git history, and path inventories:

  • Earlier reproduction notes, inventories, and extraction records were read in full, including potential defects previously rejected or deferred.
  • A sweep of both fork issue trackers enumerated 1,358 wikijump issues and 316 ftml issues, then inspected promising defect reports to check whether the named paths and mechanisms existed at the upstream base.
  • Fork fix history was mined with git log over the divergence from upstream. Commits whose subjects contained defect, panic, error, race, overflow, or issue-reference signals were shortlisted, after which the actual diff and the upstream file at the base were inspected.
  • A mechanical path inventory listed the commits ahead of upstream in both repositories and classified commits touching paths present upstream. A later diff-level pass looked for removed lines that still existed verbatim upstream, and a further issue review looked for client-side races and destructive controls.
  • Fork-only machinery did not count as evidence of an upstream defect unless the same defective behavior could be demonstrated in unmodified upstream code; several fork fixes repaired parser, rendering, delayed-list, or compatibility machinery that upstream does not have.

Mining turned up many more candidates than pull requests. The first tracking pass recorded 126 rows, and most dropped out: they were not reproduced, were reachable only through direct RPC or database access, applied only to builds or fork state, duplicated another row, or required a product design decision before a patch would be meaningful.

How a defect was proven before any fix was written

Each concrete candidate was first tested against unmodified upstream. The preferred oracle was the real served stack in a browser (Caddy, the file service, Framerail, and Deepwell) with no fork patch applied. RPC, database, unit, and command-line probes were used for diagnosis but could not qualify a defect for a pull request on their own.

Reproductions were classified by reachability. The strongest class was reachable by an ordinary user or administrator through the normal web UI. The next required a legitimate but unusual deployment or administrative condition. Weaker classes required direct RPC, chained preconditions, database access, or unit-only proof, and the last class held unreproduced or theoretical cases. The first class became pull requests, as did the second when the fix was small and the enabling condition was stated honestly. Weaker and unreproduced rows stayed in the notes with their concrete reasons.

Where possible, reproductions used controls: paired requests with and without a cookie, browser submissions through the real form alongside a direct API control, a held network request released without altering response bodies, and byte-for-byte comparisons of before and after output. For ftml compatibility defects, the oracle was live Wikidot or a provenance-backed captured expectation, with the unmodified upstream parser run on the same input.

The regression test came after the measurement. It had to fail on the unmodified base for the measured reason before the fix was written. When a pull request splits commits, the test commit comes before the fix commit, and any remaining coverage or oracle limitations are named openly in the body.

The one exception is the Vite pull request, which relies on the published GHSA advisory and a resolved-version assertion with no local behavioral exploit reproduction.

Shape rules for each pull request

  • One logical change per pull request.
  • Keep the diff small enough for a maintainer to read; split or leave out any prospective change that conflates several endpoints, policies, or defects.
  • Do not propose the fork implementation as a large drop. Reimplement the minimum correction against upstream idioms and upstream files.
  • Use a plain imperative title that names the user-visible correction.
  • Start the body with the problem and who is harmed, in language a cold reader can understand.
  • State how the defect was reproduced on unmodified upstream, including the base commit and the control where relevant.
  • State what was not tested, what evidence is only indirect, and any reachability precondition.
  • Disclose policy or design choices plainly in the body instead of smoothing them over.
  • Identify overlapping or dependent pull requests in prose when landing order matters.
  • Do not rely on private file paths, internal task names, or unexplained process jargon in the maintainer-facing body.
  • Do not weaken a test or hardcode a captured page just to make a result pass.

Applying these rules reshaped the queue: six early broad pull requests were closed and replaced by fifteen smaller ones, while others were retitled, narrowed, given rewritten bodies, or left unchanged when narrowing would have misrepresented the measured defect.

Review simulation

The queue then went through repeated read-only reviews simulating maintainers from three perspectives: a maintainer deciding whether to keep reading, a skeptic looking for the hardest unanswered question, and a cold reader checking whether the problem, harm, evidence, and fix made sense without outside context. The criteria came from documented practice in the Linux kernel, MariaDB, LLVM, and Godot: one logical change, small and bisectable patches, test-first evidence, provenance, disclosure, and discipline around reviewer cost.

Early strict reviews caught unclear bodies that depended on private context, scope mismatches, weak oracles, unresolved internal references, and grouping problems. Preparation alternated between review and repair until the final pass accepted 45 pull requests as they stood, requiring no body repair or regrouping, and left two explicit maintainer decision points: the Vite advisory update (whose oracle is not behavioral) and the foreign-site page-create guard (which discloses its missing-category hard error, system-actor exemption, and untested bypass risk from a caller-supplied system id as design decisions).

The final review also verified that maintainer-facing bodies no longer depended on private paths or internal references. Reviewers read each Codecov comment for the specific uncovered lines, tested reachable lines where appropriate, and added short in-thread explanations for the remaining partial-verdict lines. Some pull requests have no coverage job because their changes sit outside the coverage-instrumented Rust code.

How a maintainer can use one pull request

Each pull request is self-contained:

  1. Cherry-pick it if the upstream maintainer agrees with the diagnosis, guard shape, and implementation.
  2. Use its regression test as the specification and write a fresh implementation in upstream style.
  3. Request changes; the fork owner can rebase, narrow, split, or clarify it.
  4. Close it without incorporating anything; the test and body still record the measured behavior.

Any follow-up burden falls on the fork owner. If upstream takes a different design, the fork owner can adapt the test or implementation; if upstream rejects a behavior or policy, that rejection can be recorded as a boundary so it is not proposed again. Keeping each unit small makes all of those outcomes cheap.
