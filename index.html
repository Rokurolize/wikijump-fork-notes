Fork notes for the Wikijump maintainer

Specimen pull requests, a capability comparison, and roadmap alignment from the Rokurolize forks of Wikijump and ftml.

Specimen pull requests Capability comparison Roadmap alignment Extraction method

This page collects, in one place, the material prepared for the upstream Wikijump maintainer about the Rokurolize forks of Wikijump and ftml. It has four parts: an index of 47 small demonstration pull requests that stand open on the forks (none of them submitted upstream), a capability comparison between upstream and the fork, a mapping of the unfinished items on upstream's own Project Foundation roadmap against what the fork can demonstrate, and a short account of the extraction method behind the pull requests. Everything here is a snapshot of the two repositories as inspected on 2026-11-25.

Specimen pull requests

This index covers the 47 open pull requests found live in the two forks on 2026-11-25: 33 in Rokurolize/wikijump and 14 in Rokurolize/ftml. Each entry states the defect and its user-visible effect in one sentence, based on the pull request's own title and body.

ftml, original-wiki and Wikidot-layout behavior

These pull requests concern output or link behavior measured against live Wikidot or the original wiki, including two explicitly reproduced in the Wikidot layout.

  • ftml#1424, ftml: Spaces inside raw spans render as literal spaces in the Wikidot layout instead of Wikidot's &#32;, so authors and readers comparing the two renderings see a byte-level difference.
  • ftml#1530, ftml: A multi-word element id is prefixed on every word rather than once as a whole, so anchors, links, or scripts that target the live-Wikidot id no longer match the rendered id.
  • ftml#1534, ftml: A local page whose name looks like a URL scheme, such as data:example, is rendered as #invalid-url instead of as a local page link, making the page unreachable through ordinary links.
  • ftml#1565, ftml: Uppercase and lowercase spellings of the same hex color serialize differently instead of sharing Wikidot's lowercase form, so equivalent author input produces different markup.

ftml, parser and renderer correctness

These pull requests concern malformed or edge-case wikitext that breaks parsing, rendering, or include handling.

  • ftml#1427, ftml: A triple-bracket link with an empty label and a direct target panics the renderer, so one author mistake can make an entire page unavailable.
  • ftml#1510, ftml: A block name with two trailing underscores, such as [[div__]], crashes the parser instead of producing a parse error, so readers get an error page rather than the article.
  • ftml#1511, ftml: Overlapping [[include]] directives can clobber replacement ranges or panic the renderer, leaving readers with broken content or no page.
  • ftml#1517, ftml: An include whose page reference is only a separator is accepted with an empty page name instead of being rejected, causing an unintended fetch or misleading missing-page result.
  • ftml#1536, ftml: A bibliography citation whose label is only whitespace produces a broken reference without a parse error, leaving authors no warning and readers a citation that leads nowhere.
  • ftml#1537, ftml: A whitespace-only category condition silently renders its body instead of producing a parse error, so content that should have been filtered can appear.
  • ftml#1538, ftml: A list whose only item line is whitespace renders empty list tags without a parse error, so the intended list disappears with no warning.
  • ftml#1539, ftml: A ruby annotation with an empty base or reading renders a half-empty pronunciation guide without a parse error, leaving visibly broken markup.
  • ftml#1564, ftml: Leading document whitespace can prevent a quote or list marker at the first non-empty line from becoming structure, so a saved page renders the marker as plain text.
  • ftml#1566, ftml: The null includer reports an internal invalid-return error instead of removing include blocks, so tests and tooling that render without fetching includes get no page at all.

Wikijump, browser-visible page and file workflows

These pull requests concern controls, forms, races, and paging in the served page and file interface.

  • wikijump#3908, wikijump: Saving site settings fails on an imported site whose site-user relation still uses the legacy user spelling, so an administrator's ordinary settings edit is rejected.
  • wikijump#3911, wikijump: A delayed initial file-list response can overwrite the deleted-file list after Restore is opened, so a moderator loses the deleted rows and Restore controls they were using.
  • wikijump#3912, wikijump: Racing revision requests can let an older answer overwrite a newer one, so a reader comparing revisions sees a revision they did not most recently select.
  • wikijump#3913, wikijump: A late file-history response is not bound to the file that requested it, so one attachment can display another attachment's revisions and Revert controls.
  • wikijump#3918, wikijump: The Files pane's Revert control requests an action that is implemented but not registered, so the editor who clicks it receives a 404 instead of a rollback.
  • wikijump#3919, wikijump: Saving a file edit omits the client address required by the backend audit call, so every save from the Files pane fails with a parameter error.
  • wikijump#3927, wikijump: An anonymous Restore form submission is rejected for missing user_id instead of producing a clean permission error, so a visitor sees a raw server error.
  • wikijump#3936, wikijump: Tags submitted through the create form or page_create API are silently discarded, so a newly created page has no tags even though later edits save them correctly.
  • wikijump#3986, wikijump: The fileList action ignores its page and perPage arguments and returns every file every time, making large attachment lists unnecessarily expensive for clients.
  • wikijump#3990, wikijump: The deleted-page Restore form always submits page id 0 regardless of the selected radio button, so the restore fails and the page stays deleted.

Wikijump, sessions, routing, and request-boundary validation

These pull requests concern how requests, cookies, slugs, and API parameters are interpreted before page behavior runs.

  • wikijump#3881, wikijump: A NUL byte in a page name or RPC string parameter turns ordinary lookups into internal errors, so an unauthenticated crafted URL can produce a site-wide 500 response.
  • wikijump#3915, wikijump: A stale or invalid session cookie makes every page return HTTP 500 until the visitor manually clears cookies, while the same pages work without the cookie.
  • wikijump#3934, wikijump: A slug containing a character above U+00FF cannot be carried in the internal page header, so Japanese and other non-Latin-1 page URLs return 500 and cannot even be created through the form.

Wikijump, authentication, authorization, and permission boundaries

These pull requests concern missing or incorrect permission checks on accounts, pages, files, and site settings.

  • wikijump#3882, wikijump: A soft-deleted user can still log in and receive a fresh session, so administrative deletion does not lock the account out.
  • wikijump#3943, wikijump: A user without delete permission can delete and restore another user's page, with both state changes attributed to the unauthorized account.
  • wikijump#3947, wikijump: A user denied edit access can still roll a page back, silently altering revision state that anonymous readers can observe.
  • wikijump#3952, wikijump: A non-member can change another page's layout, rename it, and set its parent because none of those mutations checks edit permission first.
  • wikijump#3953, wikijump: A non-member can create and remove page locks even though the user lacks the lock permission, changing whether editors can use the page.
  • wikijump#3954, wikijump: An authenticated user can create a page in a foreign site by supplying that site's id, so the page appears where the user has no create permission.
  • wikijump#3957, wikijump: A logged-in outsider can read another site's wikitext, revision history, and file list through page read actions because those reads omit the view-permission check.
  • wikijump#3958, wikijump: File revision history ignores the requested site and page, so an outsider can read another site's file revisions by supplying identifiers.
  • wikijump#3959, wikijump: A user with no site role can delete, restore, move, and upload files on another page or site because those file mutations omit the page-edit-permission check.
  • wikijump#3960, wikijump: A user with no site role can overwrite another site's settings, including its tagline, simply by supplying that site's numeric id.

Wikijump, votes and deleted-page state

These pull requests concern rating writes that either escape the rating model or survive after their target is gone.

  • wikijump#3955, wikijump: The vote API still accepts vote changes, disabling, and removal for deleted or missing pages, so ratings keep moving on content that no longer exists.
  • wikijump#3956, wikijump: The vote API accepts arbitrary 16-bit values rather than only -1 and 1, allowing undefined vote values that distort computed scores.

Wikijump, file serving, error pages, and information exposure

These pull requests concern the public files origin, upload metadata, crafted-request failures, and details exposed in errors.

  • wikijump#3879, wikijump: Direct requests to the files service without its internal routing headers panic the handler and drop the connection instead of returning an HTTP error response.
  • wikijump#3880, wikijump: A crafted files-origin error URL interpolates request text into HTML without escaping, executing script for a victim who follows the link.
  • wikijump#3909, wikijump: Uploaded files are stored and served with a byte-sniffed content type rather than the browser-declared type, so visitors receive a Content-Type different from the one the upload declared.
  • wikijump#3935, wikijump: A well-formed but missing text-block index panics the handler and produces an empty 502 instead of a clean error response.
  • wikijump#3961, wikijump: A file URL containing a NUL byte returns a 500 error page reflecting the NUL instead of a normal 404.
  • wikijump#3962, wikijump: An avatar URL whose id is not numeric returns an empty 500 response instead of the normal templated 404.
  • wikijump#3987, wikijump: Named-action failures can expose Rust source paths, line numbers, or raw PostgreSQL driver text in client-visible error traces, leaking implementation detail to ordinary callers.

Wikijump, dependency security

This pull request is a dependency-security update rather than a behavioral reproduction.

  • wikijump#3883, wikijump: Vite 7.3.7 is affected by a critical dev-server remote-code-execution advisory when the server is network-exposed, so the dependency is moved to the patched 7.3.8 release.

Decision points disclosed in the pull requests

Two entries are decision points rather than ordinary defect demonstrations: wikijump#3883 relies on the published Vite security advisory plus a resolved-version assertion rather than a local behavioral test, and wikijump#3954 discloses the guard-shape choices a maintainer must judge: a missing category is a hard error rather than an invented category-0 fallback, the internal system actor is deliberately exempt so seeding and migrations still work, and the untested caller-supplied-system-id bypass risk is named explicitly.

Stage 1 (Foundations), epic WJ-1256, live status Backlog

1. "All UI available so far is properly localized (i.e. no UNTRANSLATED)"

  • Jira status: WJ-1262, "Ensure all UI is properly localized", Backlog.
  • Upstream today: partial. A scan of the upstream base found UNTRANSLATED in 16 files under framerail/src, deepwell/src, or locales/fluent; the upstream /about page itself displays UNTRANSLATED: Info page and UT: labels.
  • Fork today: the same scan found no UNTRANSLATED marker in the fork trees inspected. The fork has 53 Fluent files, and the running fork-backed local mirror rendered /-/about in localized English or Japanese depending on the site.
  • Extraction prospect: demonstration. This is broad cumulative UI work, not one defect. The fork can show the localized pages and its translation keys, but upstream would still need its own review of coverage and missing languages.

2. "All infrastructure is available through IPv6"

  • Jira status: WJ-1261, "Ensure Wikijump is fully IPv6-capable", Backlog.
  • Upstream today: unproven. The upstream tree contains local IPv6 bind examples such as [::1]:2747 and PostgreSQL ::1/128 rules, but no evidence of end-to-end public IPv6 deployment.
  • Fork today: no meaningful advantage. The fork carries the same local examples but no additional proof of full IPv6 infrastructure.
  • Extraction prospect: not applicable. This is primarily deployment and network validation, not a code object that can be handed over.

3. "Page theme exposure"

  • Jira status: no directly corresponding issue was found in the stage epic; WJ-113 "Base theme support" is Backlog outside the stage epic.
  • Upstream today: partial. Upstream exposes page/site layout selection (Layout::Wikidot or Layout::Wikijump) in LayoutPane.svelte and the admin screen, and framerail/src/routes/+layout.svelte hardcodes a Sigma-style Wikidot base-theme import, but no theme-management or per-category selection surface was found.
  • Fork today: ThemeSettings.svelte exposes theme type, built-in theme, external URL, and custom CSS fields by category; the fork also has theme evidence and replay tooling in install/local/theme-lab/ and docs/agents/theme-lab.md.
  • Extraction prospect: demonstration. The fork can demonstrate a working theme model and imported theme evidence, but the implementation is tied to the fork's larger Wikidot shell and category model rather than being a small patch.

4. "Temporary support for passcode to limit user creation" (unchecked child of the completed user-creation UI item)

  • Jira status: no exact issue found. Related WJ-1153, "Add platform setting to deny new user creation", is Backlog.
  • Upstream today: no passcode flow found. Upstream has an authorization-token type whose comment says it can authorize user creation when registrations are disabled, but that is not passcode-based self-service registration.
  • Fork today: no passcode flow found. The fork has an allow_registration configuration switch and registration rate limiting in deepwell/src/endpoints/user.rs, but neither is the roadmap's temporary passcode mechanism.

Extraction method

This document describes the method used to extract small, reviewable defect demonstrations from the long-lived Rokurolize/wikijump and Rokurolize/ftml forks. It is neutral process documentation for the owner's use, not a message to the maintainer.

Starting point

The method treats the fork implementations as evidence, not as code to be upstreamed wholesale. The portable unit is a behavior that can be proven against unmodified upstream: a failing input, request, browser workflow, API call, or externally published advisory, followed by a small native correction.

The upstream bases were fixed before extraction. Wikijump pull requests were cut from upstream commit 324cbef61145aadcf016ff6e8e4a8c83cdae48f0; later ftml pull requests were cut from 3ea7d6d00995ee6c0b7fc32fa50f38a5eb2446dc, with the two earliest ftml entries originally cut from the immediately preceding mirror base 81552b44d3da5a1daea1bf43f4d5fa9b5c1a5cbe. A local unmodified-upstream laboratory was rebuilt and reseeded at the wikijump base before behavioral reproductions.

How prospective defects were found

Potential defects came from several independent streams rather than from reading fork diffs alone:

  • Earlier reproduction notes, inventories, and extraction records were read in full, including potential defects that had previously been rejected or deferred.
  • Both fork issue trackers were swept. The first pass enumerated 1,358 wikijump issues and 316 ftml issues, then inspected promising defect reports and checked whether the named paths and mechanisms existed at the upstream base.
  • Fork fix history was mined with git log over the divergence from upstream. Subjects containing defect, panic, error, race, overflow, or issue-reference signals were shortlisted, after which the actual diff and the upstream file at the base were inspected.
  • A mechanical path inventory enumerated the ahead-set in both repositories and classified commits touching upstream-present paths. A later diff-level pass looked for removed lines that still existed verbatim upstream, and a further issue review looked for client-side races and destructive controls.
  • Fork-only machinery was excluded as evidence of an upstream defect unless the same defective behavior could be demonstrated in unmodified upstream code. This mattered because several fork fixes repaired parser, rendering, delayed-list, or compatibility machinery that upstream does not have.

Mining produced many more potential defects than pull requests. The first tracking pass recorded 126 rows; most were not reproduced, were only reachable through direct RPC or database access, were build-only or fork-state-only, duplicated another row, or required a product design decision before a patch would be meaningful.

How a defect was proven before any fix was written

Each concrete possibility was tested against unmodified upstream first. The preferred oracle was the real served stack in a browser: Caddy, the file service, Framerail, and Deepwell, with no fork patch applied. RPC, database, unit, or command-line probes were used for diagnosis but did not by themselves qualify a defect for a pull request.

Each reproduction was classified by reachability rather than treated as equally important. The strongest class was ordinary user or administrator reachability through the normal web UI. The next class required a legitimate but unusual deployment or administrative condition. Weaker classes required direct RPC, chained preconditions, database access, or unit-only proof; unreproduced or theoretical possibilities formed the final class. Only the first class, and the second class when it had a small fix and an honestly stated enabling condition, became pull requests. Weaker and unreproduced rows remained in the notes with their concrete reasons.

Reproductions used controls where possible. Examples include paired requests with and without a cookie, browser submissions through the real form plus a direct API control, a held network request followed by release without changing response bodies, and byte-for-byte comparisons of before and after output. For ftml compatibility defects, the oracle was live Wikidot or a provenance-backed captured expectation, then the unmodified upstream parser was run on the same input.

Only after that measurement existed was a regression test written. The test was required to fail on the unmodified base for the measured reason. The fix was written afterward. Where a pull request carries separate commits, the test commit precedes the fix commit; where coverage or oracle limitations remain, the body names them rather than implying stronger evidence.

One exception is explicitly disclosed rather than hidden: the Vite pull request is advisory-driven. Its evidence is the published GHSA advisory and a resolved-version assertion, not a local behavioral exploit reproduction.

Shape rules for each pull request

The extraction rules were:

  • One logical change per pull request.
  • Keep the diff small enough for a maintainer to read; when one prospective change conflated several endpoints, policies, or defects, split it or leave it out.
  • Do not propose the fork implementation as a large drop. Reimplement the minimum correction against upstream idioms and upstream files.
  • Use a plain imperative title that names the user-visible correction.
  • Start the body with the problem and who is harmed, in language a cold reader can understand.
  • State how the defect was reproduced on unmodified upstream, including the base commit and the control where relevant.
  • State what was not tested, what evidence is only indirect, and any reachability precondition.
  • Disclose policy or design choices inside the body instead of smoothing them over.
  • Identify overlapping or dependent pull requests in prose when landing order matters.
  • Do not rely on private file paths, internal task names, or unexplained process jargon in the maintainer-facing body.
  • Do not weaken a test or hardcode a captured page merely to make a result pass.

Applying these rules changed the queue. Six early broad pull requests were closed and replaced by fifteen smaller successors. Other pull requests were retitled, rebodied, narrowed, or left unchanged when narrowing would have misrepresented the measured defect.

Review simulation

The queue then went through repeated read-only simulated-maintainer reviews. Reviewers used three perspectives: a maintainer deciding whether to keep reading, a skeptic looking for the hardest unanswered question, and a cold reader checking whether the problem, harm, evidence, and fix could be understood without outside context. The criteria were derived from documented practice in the Linux kernel, MariaDB, LLVM, and Godot: one logical change, small and bisectable patches, test-first evidence, provenance, disclosure, and reviewer-cost discipline.

The first strict reviews were negative. They found bodies that were unclear without private context, scope mismatches, weak oracles, unresolved internal references, and grouping problems. Preparation alternated between review and repair until the final review concluded that 45 pull requests were acceptable as they stood, none required body repair, none required regrouping, and two remained explicit maintainer decision points. Those two are the Vite advisory update, whose oracle is not behavioral, and the foreign-site page-create guard, whose missing-category hard error, system-actor exemption, and untested caller-supplied-system-id bypass risk are disclosed as design decisions.

The final review also verified that the maintainer-facing bodies no longer depended on private paths or internal references. Separately, Codecov comments were read rather than merely checked for presence. Reachable uncovered lines were tested where appropriate; remaining partial-verdict lines received short in-thread explanations. Some pull requests have no coverage job because their changed surface is outside the coverage-instrumented Rust code.

How a maintainer can consume one pull request

Each pull request is self-contained and can be consumed in several ways:

  1. Cherry-pick it if the upstream maintainer agrees with the diagnosis, guard shape, and implementation.
  2. Use its regression test as the specification and write a fresh implementation in upstream style.
  3. Request changes; the fork owner can rebase, narrow, split, or clarify it.
  4. Close it without incorporating anything; the test and body still record the measured behavior.

The expected follow-up burden belongs to the fork owner, not the maintainer. If upstream takes a different design, the fork owner can adapt the test or implementation. If upstream rejects a behavior or policy, the rejection can be recorded as a boundary rather than repeatedly re-proposed. The point of the method is to make each unit small enough that any of those outcomes is cheap.
